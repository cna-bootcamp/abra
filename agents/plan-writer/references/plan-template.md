## 2. §4.0 디렉토리 구조 — 표준 트리

**루트 규칙 (develop 파이프라인과의 컨트랙트)**

- 애플리케이션 코드는 반드시 `app/` 루트 아래에 둠 (`src/` 금지 — develop 스킬 MUST NOT 규칙)
- `app/main.py`, `app/api/routes.py`는 develop 스킬 Phase 4(챗봇 생성)·Phase 5(E2E 테스트)가 전제로 하는 필수 진입점

**표준 트리 예시 (Option A — Python/FastAPI)**

```text
<project>/
├── app/
│   ├── api/
│   │   └── routes.py   # HTTP 엔드포인트 (develop 파이프라인이 참조)
│   ├── graph/          # LangGraph StateGraph, state.py, edges.py
│   ├── nodes/          # DSL 노드별 1:1 구현
│   ├── mcp_server/     # Streaming HTTP MCP 서버
│   ├── mcp_client/     # 테스트용 MCP Client 앱
│   ├── storage/        # 필요 시: 세션/이벤트/배포/성과 저장
│   ├── scheduler/      # 필요 시: 후속 알림/예약 작업
│   ├── auth/           # 필요 시: 인증/권한/비밀관리
│   ├── files/          # 필요 시: 이미지·파일 입력 처리
│   └── main.py         # 엔트리포인트 (FastAPI 앱 인스턴스)
├── tests/
│   ├── unit/
│   ├── integration/
│   └── e2e/
├── deploy/
└── README.md
```

**필수 디렉토리**
`app/graph`, `app/nodes`, `app/mcp_server`, `app/mcp_client`, `app/api`, `tests`

**조건부 디렉토리**
`app/storage`, `app/scheduler`, `app/auth`, `app/files`는 시나리오·NFR 요구가 있을 때만 포함.

각 파일 옆에는 한 줄 설명을 붙여 역할을 명확히 함.

## 3. §4.1 ~ §4.7 세부 작성 가이드

### §4.1 DSL 노드 ↔ 파일 매핑

- DSL의 `llm`, `code`, `question-classifier` 노드를 빠짐없이 표로 매핑
- 최소 컬럼: `DSL 노드 ID`, `DSL Title`, `노드 유형`, `<role>`, `산출 파일`, `비고`
- `[MOCK]` 여부, 프로덕션 전환 필요 여부를 함께 표시
- 표 행 수는 §4.0 트리의 `app/nodes/` 하위 파일 수와 일치해야 함

### §4.2 핵심 워크플로우

- DSL의 실제 분기와 LangGraph 실행 순서를 단계적으로 기술
- "어떤 입력이 들어오면 어떤 경로를 타는지" 설명
- 조건 분기, 반복, 종료 조건, state 변경 포인트 포함

### §4.3 입출력 인터페이스

- MCP 도구 기준 입력/출력 예시를 JSON 또는 표로 제시
- 필수/선택 필드, 타입, 기본값, 검증 규칙 명시
- 스트리밍 응답이면 청크 구조 또는 최종 응답 구조 설명
- 파일 입력이 있으면 파일 메타데이터와 처리 흐름 포함

### §4.4 외부 도구 연동

- 외부 API, 검색, 스토리지, 워커 등 외부 의존성을 표로 정리
- 각 항목마다 `용도`, `입력`, `출력`, `실 구현 여부`, `모킹 전략`, `전환 조건` 명시
- MCP 도구가 여러 개라면 도구별 책임과 호출 시점 구분

### §4.5 시나리오-DSL 갭 및 커스텀 개발 범위

- `gap_analysis`를 그대로 요약하지 말고 개발계획 관점으로 재구성
- 최소 항목: `요구사항`, `출처(scenario/dsl/gap)`, `이번 스프린트 처리 방식`, `제외 시 영향`, `후속 스프린트 제안`
- DSL에 없지만 시나리오에 있는 요구사항은 반드시 여기에 등장해야 함

### §4.6 에러 핸들링

- 실패 유형을 사용자 입력, 내부 처리, 외부 API, 저장소, 인증, 스케줄링으로 나눠 기술
- 각 에러마다 `감지 방식`, `복구/재시도 전략`, `사용자 노출 메시지`, `로깅/알림` 명시
- `[MOCK]` 노드의 실패 시나리오와 프로덕션 전환 후 차이 포함

### §4.7 개발 순서 및 일정

- 구현 순서를 의존성 기준으로 나열
- 각 단계마다 `기간`, `주요 산출물`, `선행조건`, `완료 기준`, `리스크` 명시
- 특화질문으로 드러난 요구사항이 별도 트랙이면 본 개발 순서에 편입 시점 명시

## 4. 자가검증 게이트 체크리스트

### Hard Gate (필수 — 실패 시 재작업)

- **H1**: 9개 섹션 제목이 `## 1. 개요` ~ `## 9. 배포 계획`으로 정확히 일치
- **H2**: §4.0 디렉토리 구조 트리 존재
  최소 `app/graph`, `app/nodes`, `app/mcp_server`, `app/mcp_client`, `app/api`, `tests` 포함
  (`src/` 루트 금지 — develop 스킬 컨트랙트)
  `app/main.py`, `app/api/routes.py`가 트리에 명시되어 있음
- **H3**: §4.1 매핑 테이블 행 수 == DSL의 `llm` + `code` + `question-classifier` 노드 수
  **검증 절차**: 저장 직전 `{tool:file_read}`로 입력 DSL yaml을 다시 읽어
  `nodes` 배열을 순회하며 `type ∈ {llm, code, question-classifier}` 노드 수 **N**을 산출한 뒤,
  §4.1 매핑 테이블의 데이터 행 수가 **N**과 일치하는지 확인.
  응답 본문에 `DSL 재파싱 결과 N=<값>, §4.1 행 수=<값>` 로그 포함.
- **H4**: §4.0 트리의 `app/nodes/` 하위 파일 수 == §4.1 매핑 테이블 행 수
  **검증 절차**: H3에서 산출한 **N**을 §4.0 트리의 `app/nodes/` 하위 파일 수와 비교.
  응답 본문에 `app/nodes/ 파일 수=<값>` 로그 포함.
- **H5**: 각 `app/nodes/<role>.{py|ts}`의 `<role>`이 DSL 대응 노드 `title`로부터
  도출 알고리즘에 의해 변환됨
- **H6**: MCP 서버는 Streaming HTTP 전송으로 기술되고,
  `POST /mcp` 단일 엔드포인트가 §6에 존재
- **H7**: §2 LLM 래퍼가 DSL `model.provider` 값에서 도출되며, DSL에 없는 제공자는 기재되지 않음
- **H8**: 시나리오에 파일·이미지 입력 요구가 있으면 처리 모듈 또는 제외 사유가 계획서에 존재
- **H9**: 시나리오에 시간 기반 후속 작업 요구가 있으면 스케줄러/워커/저장소 설계가 존재
- **H10**: 보안 요구가 `높음`이거나 외부 API가 있으면 인증/권한/비밀관리/감사로그 설계가 존재
- **H11**: Dockerfile, compose, CI 스니펫이 베이스 이미지와 의존성 가정에 모순되지 않음

### Business Gate (요구사항 반영)

- **B1**: 기술스택(§2)이 NFR `common.stack` 값과 일치
- **B2**: 배포 계획(§9) 산출물이 NFR `common.deployment` 값과 일치
- **B3**: 테스트 전략(§8)의 E2E가 `scenario.md`의 Given-When-Then과 1:1 매핑
- **B4**: §5 프롬프트 최적화가 DSL의 모든 `llm` 노드를 5단계로 점검
- **B5**: §7 데이터 모델이 DSL `start` 입력 변수와 `end`/`answer` 출력 구조를 반영
- **B6**: `scenario.md`의 검증 시나리오가 E2E 표와 구현 범위에 모두 반영됨
- **B7**: 제외 요구사항은 향후 스프린트만 적지 않고, 제외 사유와 사용자 영향도를 함께 명시
- **B8**: `nfr.special`의 각 항목이 계획서의 최소 1개 이상 섹션에 반영됨

### Soft Gate (품질 권장)

- **S1**: `[MOCK]` 코드 노드가 에러 핸들링 또는 개발 순서에 "프로덕션 전환 필요"로 명시
- **S2**: §9 롤백 전략 기술
- **S3**: 라이브러리 버전 범위가 `^x.y` 형식으로 기재
- **S4**: §3 아키텍처 다이어그램이 MCP Client → MCP Server → LangGraph 경로를 포함
- **S5**: 시나리오-DSL 갭 표가 우선순위와 구현 결정을 함께 제공
